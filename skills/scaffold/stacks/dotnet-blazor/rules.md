# .NET Blazor standards: {{component name}}

Sources: the Microsoft C# coding conventions (https://learn.microsoft.com/dotnet/csharp/fundamentals/coding-style/coding-conventions), the .NET code style rules, the Blazor documentation and the common container / presentational component layering. `.editorconfig` with `dotnet format` checks formatting and naming, the .NET analyzers catch common problems during the build, and `ArchitectureTests` (ArchUnitNET) checks layering. This file covers what needs judgment.

## Layers: pages and presentational components

```
src/<project>/
├── Features/<feature>/
│   ├── Pages/          pages: components with an @page route
│   ├── Components/     presentational components
│   ├── Services/       business logic, API calls
│   ├── Data/           data access (EF Core DbContext, repositories)
│   └── Models/         type definitions
├── Shared/Components/  presentational components shared by features
└── Components/         App, routes, layout (generated by the template)
```

**Pages (container components)** decide where data comes from and where it goes: they inject services, call business logic and APIs, handle loading, errors and empty data, and hold state; they pass data to children through `[Parameter]` and update state through the children's `EventCallback`; when parent and child must keep one value in sync they use `@bind-<parameter>` two-way binding.

**Presentational components** decide only what things look like:

- Stateless: data comes in only through `[Parameter]` and changes go out only through `EventCallback`. Internal state is limited to pure UI state such as expanded or collapsed.
- They inject nothing (no `@inject`, no `[Inject]`), call no APIs and do not touch the database. Whatever data they need, the page passes in.
- Given parameters, they render on their own and can be tested in isolation with bUnit.

Enforced by `ArchitectureTests`: presentational components (`Features/*/Components`, `Shared/Components`) inject nothing and do not depend on Services or Data; features do not depend on each other.

## Writing components

- Every page and component states its render mode (`@rendermode`) explicitly, matching the architecture's choice.
- Lists rendered in loops use `@key`.
- `[Parameter]` only receives data from the parent and is never changed inside the component; copy it to a private field when it must change.
- Components that subscribe to events or hold resources implement `IDisposable` or `IAsyncDisposable` and release them there.
- Components with a lot of logic use code-behind (`.razor.cs`).
- Avoid JS interop; when it is unavoidable, wrap it in a service called by the page.

## Services and data

- Choose dependency injection lifetimes carefully. Under Blazor Server a user connection (circuit) lives a long time, so do not inject a Scoped DbContext straight into components; use `IDbContextFactory<T>` and create one per operation.
- Configuration is bound with the Options pattern (`IOptions<T>`).
- Secrets use user-secrets during development and environment variables or a secret store in production, never `appsettings.json`.
- Schema changes use EF Core migrations.

## Async code

- Async all the way down; no `.Result` or `.Wait()`.
- Operations that may take a while accept a `CancellationToken`.
- External services are called with an HttpClient created by `IHttpClientFactory`, with a timeout.

## Styles

- Colors, font sizes and spacing come from design tokens (CSS custom properties, `var(--...)`), never hard-coded colors or pixel values.
- Component styles use CSS isolation (`<component>.razor.css`) and never override child components or global styles.

## Coding habits

- Nullable reference types are on. Do not silence warnings with `!` unless you can say why the value is never null.
- Logs use `ILogger<T>` structured logging, `logger.LogInformation("Order {OrderId} paid", id)`, never string concatenation; never log passwords, tokens or complete personal data.
- Amounts use decimal; stored times are UTC `DateTimeOffset`.

## Tests

- Services: xUnit tests of the business logic; presentational components: bUnit tests of "given these parameters, what renders and which callback a click triggers".
- Use a real test database (e.g. Testcontainers), not the EF Core in-memory provider pretending to be one.
