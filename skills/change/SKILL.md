# 变更分诊

新想法进来时，先弄清它动了项目的哪一层，再决定要做多少事：小改动直接开发，大变化要先回头改需求和架构，不能直接写代码。

## 分级

| 级别 | 判断依据 | 例子 | 要做的事 |
|---|---|---|---|
| L0 修 bug | 现有需求的验收标准没有被满足 | 按钮点了没反应 | 确认有能复现的 issue，交给 /implement |
| L1 新功能，需求范围内 | 符合现有目标，不和现有需求冲突，架构不用变 | 列表加个排序 | 1 到 2 轮补问，新增 REQ，拆 issue |
| L2 需求变了 | 修改或推翻已有的 REQ，或者新增的需求和已有需求有冲突 | 原来只给个人用，现在要支持团队 | 找出所有受影响的 REQ 和代码，补问，更新需求，规划迁移 |
| L3 目标变了 | 目标用户、成功标准或范围变了 | 从工具变成平台 | 重新过 vision，再评估架构，可能升级为 L4 |
| L4 架构变了 | 现有架构满足不了：规模、技术栈、组件划分、部署方式要变 | 单体要拆出一个独立服务 | 用 /architect 写新的 ADR 和迁移步骤，再拆 issue |

一个想法可能同时涉及多级，按最高的那级处理。

## 提问方式

和 /kickoff 一样：用 AskUserQuestion，每轮 2 到 4 个问题，每题 2 到 4 个具体选项，推荐的放第一个并标"（推荐）"。补问只问这次变更相关的内容。

## 步骤

### 0. 读现状

- 输入是 issue 编号时：`gh issue view <编号> --comments`。
- 读 CLAUDE.md、`docs/README.md`、`docs/product/`、`docs/architecture/overview.md`、`docs/adr/`、`docs/roadmap.md`。
- 在代码里搜索相关的部分，弄清现在是怎么实现的。

### 1. 定级

说清楚：这个变更碰到了哪些 REQ、哪些 ADR、哪些组件和代码，所以判定为哪一级。用 AskUserQuestion 请用户确认级别（推荐项是你的判断）。

### 2. 按级别处理

**L0**：没有 issue 就用 bug 模板的结构创建一个（复现步骤、期望、实际），标签 `type:bug`。问清楚复现条件。然后跳到第 4 步。

**L1**：
1. 对照 kickoff 技能 `references/requirement-holes.md`（与本技能同级的 kickoff 目录）里相关的条目，问 1 到 2 轮：谁用、怎么用、边界和异常、和现有功能怎么配合。
2. 在 `docs/product/requirements.md` 里新增 REQ，编号接着往下排。
3. 用 /roadmap 的 issue 格式拆出 issue（本技能直接按 roadmap 技能 `templates/issue.md` 的结构写），放进合适的里程碑。

**L2**：
1. 列出受影响的 REQ、相关代码和已有数据。
2. 补问：新规则是什么、旧数据怎么处理、新旧行为要不要并存一段时间、要不要功能开关。
3. 更新 requirements.md：改动的 REQ 直接修改并注明修改日期；被推翻的 REQ 标为"已废弃，被 REQ-xxx 替代"，写新的 REQ。
4. 检查对架构的影响：需要改架构时升级为 L4。
5. 拆 issue，包括数据迁移和清理旧代码的 issue。

**L3**：
1. 补问新目标、新用户、新成功标准、新范围，更新 `docs/product/vision.md`。
2. 逐条检查现有 REQ 是否还成立，按 L2 的方式更新。
3. 对照新的规模和约束检查架构，需要变时升级为 L4。
4. 更新 roadmap：不再需要的 issue 关闭并写明原因，新工作拆成 issue。

**L4**：
1. 用 Skill 工具运行 `architect`，说明这是架构变更以及变更的原因。它会写新的 ADR 和迁移步骤。
2. 把迁移步骤拆成 issue：每一步都能单独上线、单独回滚；新旧实现并存期间用功能开关切换。

### 3. 写变更记录

L2 及以上，按 `templates/change-record.md` 写 `docs/changes/<YYYY-MM-DD>-<简述>.md`：变了什么、为什么、影响了哪些文档和代码、做了哪些决定、拆出了哪些 issue。

### 4. 提交和交接

- 文档改动走 `docs/` 分支，提交信息 `docs(product): <内容>` 或 `docs(architecture): <内容>`，用 /open-pr 合并。
- 需要在 GitHub 上新建或关闭 issue 时，先把清单给用户看，同意后再操作。
- 告诉用户：可以运行 `/implement <issue 号>` 开始开发。
